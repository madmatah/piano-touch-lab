# Configuration

## Modules

- **A module is one directory of a layer.** The project is a single unit, with one `package.json`, one `bun.lock` and one `tsconfig.json`: a module's layer is its directory, as `.claude/rules/architecture.md` > Layers lists them, and a module whose folder has an `index.ts` exposes only what it exports.
- **The documents list every module.** A change that adds, renames or removes a module, or changes its layer or its dependencies on other modules, updates its row in `docs/foundations.md` > Layers and modules in the same change.
- **`src/components/ui/` is generated.** Its components are added with the shadcn CLI (`bunx shadcn add <component>`), in the new-york style with lucide icons, as `components.json` configures it. A component the CLI cannot add is written in the form the CLI gives. The folder is left out of ESLint and Prettier, since its code follows shadcn's style.

## Dependencies

- **A new dependency comes from a known, maintained publisher, under a permissive license:** MIT, ISC, BSD, Apache-2.0 or 0BSD for code, and the SIL Open Font License for fonts. The project is dedicated to the public domain under the Unlicense, which a copyleft license would bind to its own terms.
- **A dependency is declared for what it does:** a library the shipped code imports goes in `dependencies`, a tool of the gate or the build in `devDependencies`, and a package that nothing imports any more leaves `package.json`.
- **Never weaken what the lockfile guarantees.** `bun.lock` is committed, and the CI and the deploy install from it with `bun install --frozen-lockfile`, which never changes it. No setting lets an install bypass or override it, such as another registry. A tool that no lockfile holds is pinned where it is installed: Bun by the `packageManager` field of `package.json`, which setup-bun reads, and the Netlify CLI by its version in the deploy workflow.
- **Dependabot proposes the upgrades** of the npm packages and of the pinned actions, every week, in one pull request per upgrade or per group that `.github/dependabot.yml` declares, which passes the gate like any other. The Netlify CLI that the deploy installs is upgraded by hand.

## Continuous integration

- **Actions are pinned to full commit SHAs,** each with its version label beside it, because a tag can move to other code. Three of them come from third parties: `oven-sh/setup-bun`, `jsmrcaga/action-netlify-deploy`, which receives the Netlify token, and `guibranco/github-status-action-v2`, which receives the GitHub token to post the commit status.
- **Permissions stay read-only.** The one write is `statuses` in the deploy, whose last step posts the address of the deploy on the commit. The checkout keeps no credentials (`persist-credentials: false`).
- **Only the step that deploys sees the Netlify token.** The install and the build of the demo run in steps of their own, and the deploy action, which would run them with the token in their environment, gets `true` for both commands.
- **The CI runs the gate itself,** `bun checks`, never a copy of its steps, which would drift from it.
- **Event data reaches a `run:` script only through `env:`,** never through `${{ }}` inside the script, where it would be spliced into shell code.
- **No `pull_request_target` workflow checks out untrusted code, and no secret reaches a run from a fork,** since either would hand the repository's credentials to code from outside. A pull request from a fork gets no Netlify token, so its deploy fails without leaking it.

## Checks

- **A check that enforces a rule is never narrowed to let a change pass:** in ESLint, TypeScript, Prettier, the translation checks or any other tool of the gate, no file excluded, no rule turned off or lowered to a warning, no threshold loosened, and no step dropped from `bun checks` or from its CI run. A change to the rule itself changes its rules file and its check together, and says why.
- **A rule that ESLint enforces is an error,** since a warning lets `bun checks` pass and enforces nothing.
- **The exclusions that stand, and why:** `src/components/ui/` is generated by shadcn; `dist/` is build output; `bun-env.d.ts` declares the modules Bun imports as files; `eslint.config.js` is the linter's own configuration. `build.ts` and `config/` are outside ESLint and the type checker, and `config/` outside Prettier too, a gap to close (planned) rather than a rule. ESLint lets `scripts/` use `console`, since the terminal is a script's whole output.
